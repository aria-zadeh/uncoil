# Pinned toolchain for train/.venv-export12: executorch 1.2.0, chosen to match
# the ExecuTorch runtime react-native-executorch 0.9.3 embeds (1.2.0), rather
# than the 1.4.1 in train/.venv-export, whose forward compatibility with the
# app's older embedded runtime is not guaranteed. See HANDOFF.md, export
# section, for which artifact (built by which venv) to try first on device.
#
# Neither optimum-executorch release on PyPI declares an upper bound on
# executorch (both 0.1.0 and 1.1.0 say only `executorch>=1.0.0`), and only
# those two versions exist there at all - there is no 0.7.x or 1.0.x. 1.1.0
# (the same release train/.venv-export uses, paired there with executorch
# 1.4.1) is used here too, paired with executorch==1.2.0 instead; nothing in
# its metadata suggests that pairing is unsupported.
#
# torch is pinned down to 2.11.0, NOT the plain `pip install` resolve. A
# clean `pip install executorch==1.2.0 optimum-executorch==1.1.0` resolves
# torch to the newest wheel satisfying executorch's own declared
# `torch>=2.11.0` (2.13.0, same as train/.venv-export) - but executorch
# 1.2.0's compiled `_portable_lib` pybind extension does not load against
# that torch: `ImportError: DLL load failed while importing _portable_lib:
# The specified procedure could not be found` (a torch C++ ABI mismatch;
# pip's dependency resolution doesn't and can't check binary ABI
# compatibility, only the declared version range). Downgrading to
# torch==2.11.0 - executorch's own declared floor, and evidently what its
# wheel was actually built against - fixed the import. If a future
# executorch 1.2.x/1.3.x rebuild changes this, re-verify with:
#   train/.venv-export12/Scripts/python.exe -c "from executorch.extension.pybindings import portable_lib"
#
